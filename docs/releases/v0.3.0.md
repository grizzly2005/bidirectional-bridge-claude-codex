# v0.3.0 — Durable execution and delegation tracking

This experimental pre-1.0 checkpoint includes the reliability repairs since v0.2.0 and the
optional read-only delegation UI. It does not establish production safety, comparative
model performance or token savings. No npm registry package is published.

## Changes since v0.2.0

- Preserve delegation idempotency, frozen recovery contracts and total deadlines across
  retries, process interruption and same-child recovery.
- Isolate cancellation and bounded admission; require positive stop evidence before
  freeing an uncertain worker's scope. Preserve quarantine and completed business results.
- Add targeted cancellation, continuation after prelaunch contention, observation repair,
  safe diagnostic snapshots and transactional database migration checks.
- Track delegations with an opt-in dotted graph, keyboard list, paged history and attempt/
  resume details. Closing the view keeps tasks running.
- Offer an independent read-only tracking MCP server and authenticated local browser view.
  Private content stays outside the allowlisted projection; unknown metrics stay null.
- Update the canonical `using-bridge` skill and its three byte-identical project mirrors.
- Align release identities and dependencies on 0.3.0; add pinned, least-privilege GitHub
  workflows, dependency maintenance, community templates and private security reporting.

See the [changelog](../../CHANGELOG.md), [repair validation](../BRIDGE_REPAIR_VALIDATION_2026-10-02.md)
and [tracking validation](../DELEGATION_TRACKING_VALIDATION_2026-10-03.md) for details.

## Compatibility and upgrade

All six package manifests and internal workspace dependencies use **0.3.0**. The wire
protocol remains **1.3.0** and the database schema is **v4**; they are separate identities.
Schema v1–v3 databases are upgraded by the writable bridge. Older writers must not open
an upgraded database. Preserve a verified compatible code/database backup before switching.

Native Codex uses App Server by default. Legacy MCP is explicit opt-in. Recovery resumes
the same durable child and provider session; it does not create a replacement. See the
[pinned-installation and rollback guide](../BRIDGE_RELEASE_ROLLBACK.md) before a live upgrade.

## Downloads and integrity

The [GitHub release](https://github.com/grizzly2005/bidirectional-bridge-claude-codex/releases/tag/v0.3.0)
contains these assets:

| Asset | Contents |
| --- | --- |
| `bidirectional-bridge-0.3.0-source.zip` | Exact public files from the tagged Git tree |
| `bidirectional-bridge-0.3.0-compiled.zip` | The same source, lockfile, generated workspace modules and tracking HTML |
| `using-bridge-0.3.0.zip` | The complete canonical skill and references |
| `RELEASE.json` | Full source commit, tree, version and individual file SHA-256 values |
| `SBOM.cdx.json` | CycloneDX inventory of production dependencies and their recorded licenses |
| `SHA256SUMS.txt` | SHA-256 digest of every other asset |

The archive builder rejects unreviewed Git paths, source symlinks, inconsistent versions
and unexpected generated files. It does not include local databases, signing keys, raw
logs, private reports, trust state or dependencies. Dependencies are fetched from the
lockfile on the installation machine. Compiled archives contain third-party tracking UI
code with its retained license comments; dependency licenses remain distinct from MIT.

The release workflow builds from the annotated tag and creates GitHub build provenance.
Publishing with release immutability locks the tag and attached assets. A hash alone does
not authenticate its publisher: verify the release/build attestations when supported by
your GitHub CLI. See [GitHub's integrity guide](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/establish-provenance-and-integrity/verifying-the-integrity-of-a-release).

Download with an authenticated GitHub CLI or the release page:

```bash
gh release download v0.3.0 --repo grizzly2005/bidirectional-bridge-claude-codex --dir release-download
```

On Linux, run `sha256sum -c SHA256SUMS.txt` in the download directory. On Windows, use
`Get-FileHash -Algorithm SHA256` and compare each asset against the corresponding line.
Extract the compiled archive into a new directory and run:

```bash
npm ci
npm run build
npm test
npm run skills:check
npm run links:check
npm link
claude-codex-bridge --help
bridge-tracking-mcp --help
```

Keep that directory available: npm's global command shims refer to it. Replace an existing
global link only after the new installation passes. Preserve existing workspace/database
arguments. Install `skills/using-bridge/` into the client's skill directory after backing
up any existing version; all seven files, including `references/tracking-ui.md`, belong
to the skill. Both native clients must reload their MCP connection to load the new modules.

## Evidence and limits

The committed tracking validation records 499 deterministic checks and eight local browser
scenarios. The release workflow reruns the current suite, build, links, skill consistency,
material manifest, npm advisory audit, POSIX permissions and browser scenarios on the
tagged revision. Linux/Windows CI is a separate cross-platform check. Treat their actual
conclusions as the release evidence; historical totals alone do not validate a new build.

Local browser tests use a simulated adapter and the official MCP Apps protocol. They do
not call real providers or validate a user's ChatGPT account. ChatGPT requires a compatible
MCP Apps host and an authenticated private connection to the independent observer. The
release does not create that connection, expose a public endpoint, activate schedules or
implement deferred V2 task-mutation controls.
