# v0.4.0 — Shared working memory and experimental web audits

This pre-1.0 checkpoint adds continuity and web-investigation assistance to the existing
development bridge. Web Audit remains experimental. No performance, token saving or
real-program finding-rate claim is established.

## Identity and compatibility

| Layer | Version |
| --- | --- |
| Root and five bridge workspace packages / runtime | 0.4.0 |
| Independently versioned `@bridge/web-audit` | 0.1.0 |
| Wire capability marker | 1.4.0 |
| Writable SQLite schema | 6 |
| Shared-memory revision envelope | 1 |

The existing protocol SCHEMAS registry and required adapter payload shapes are unchanged
from wire1.3.0. Memory operations/types, the memory event/error and an optional inline-byte
limit are additive. This release also tightens validation of paths, read-only scopes and
contradictory verification flags, and requires current-attempt proof. Previously accepted
invalid input may now fail explicitly. Upgrade both native bridge clients together and
reload their MCP processes; an already running process retains its loaded build.
Consumers that switch exhaustively on event/error values must handle `memory.updated`
and `REVISION_CONFLICT`; the new memory JSON schemas are exported separately from SCHEMAS.

## Added

- Three on-demand MCP operations: `memory_get_context`, `memory_upsert`,
  `memory_get_changes`. Notes preserve decisions, observations, next actions and abandoned
  investigation reasons; exact scope, lifecycle, optimistic revisions and history prevent
  silent replacement. Long details remain hashed artifacts.
- Experimental JSON web-audit campaigns, CLI and skill: actor/object/state mapping,
  hypothesis planning, bounded differential GET replay/verification, refutation packets
  and abstract pattern exchange. Campaign JSON remains single-writer and holds canonical
  domain evidence. HAR/Burp ingestion is future work.
- Development and web-investigation continuity tutorials. Delegated Codex workers still
  have project bridge MCP disabled: the manager reads context, passes input artifacts and
  persists proposed deltas with output references.
- Source/compiled archives covering six workspace distributions and both canonical skills,
  with dependency inventory, RELEASE identity, SHA256 sums and workflow provenance.

## Fixed

Claude resolved inputs and stdin transport, existing-task scheduling, read-only scope
authority, byte-bounded Codex output fragments, attempt-scoped checks and preservation of a
runtime's rejected COMPLETE as PARTIAL/BLOCKED. Structure-repair stop evidence is fresh per interval.
Cross-process cancellation rereads final task state after a worker commits between polling
reads. Scheduler startup failures and simulated Windows path checks have direct regressions.
Cold Windows process inspection uses the remaining declared stop deadline; an inspection
timeout still cannot certify that a worker stopped.
Scope-directory extraction uses linear string scans while preserving existing grants;
long wildcard runs no longer trigger polynomial regular-expression work.
See the [experimental change table](../web-audit-experimental.md#bridge-changes-on-this-branch).

The SDK floor is 1.31.0 (lock 1.32.1), and proxy-addr is locked at 2.0.8.
See the [SDK advisory](https://github.com/modelcontextprotocol/typescript-sdk/security/advisories/GHSA-6qxp-vccf-f47h)
and [proxy advisory](https://github.com/jshttp/proxy-addr/security/advisories/GHSA-jqcg-44mw-7w3h).
The SDK advisory excludes the bridge's stdio clients; dependency inventory alone does not
prove exploitability.

## Install and verify

Use the source branch/PR while this checkpoint is a candidate. After the draft is qualified
and published, download the matching assets from GitHub and verify SHA256SUMS and attestations.
Published v0.3.1 tags/assets remain immutable.

The assets are `bidirectional-bridge-0.4.0-source.zip`,
`bidirectional-bridge-0.4.0-compiled.zip`, `using-bridge-0.4.0.zip`,
`bridge-web-audit-0.4.0.zip`, `SBOM.cdx.json`, `RELEASE.json` and `SHA256SUMS.txt`.
RELEASE.json records each workspace version, the source commit/tree, lockfile and file hashes.

From a source checkout/archive:

```powershell
npm ci
npm run build
npm test
node scripts/test-shared-memory.mjs
node shared/web-audit/examples/cli-smoke.mjs
```

The compiled archive needs its own `npm ci`; its distributions already exist, so rebuilding
is optional. Use Node>=22.13.0; qualification uses Node22.22.0 on Windows/Linux. Dependencies,
runtime state and client authentication are not copied from the publisher.

The memory test uses actual MCP processes/SQLite and synthetic work with no provider calls.
The web smoke uses loopback. They establish local protocol behavior; a real provider smoke
and remote CI/provenance must be examined separately on the exact candidate.

## Database migration and rollback

The experimental writer migrates schemas 1–5 to 6 on open. Do not point it at the only copy
of release state: older schema 4/5 binaries cannot reopen the upgraded database.

1. Stop writers using that database and preserve a verified SQLite backup.
2. Install the complete v0.4.0 build into a separate directory.
3. Point both callers at the same explicit migrated copy, for example
   `--db .bridge/release-0.4.0.db`; branch names alone do not isolate state.
4. Reopen the clients, inspect history and run the continuity examples.
5. For rollback, stop the new writers and reopen the untouched old database/backup with
   its matching v0.3.1 installation. Do not attempt to downgrade schema6 in place.

With the qualification Node22.22.0, the online-backup API can create the separate copy:

```powershell
node --input-type=module -e "import {DatabaseSync,backup} from 'node:sqlite';const db=new DatabaseSync(process.argv[1],{readOnly:true});try{await backup(db,process.argv[2]);}finally{db.close();}" .bridge/bridge.db .bridge/release-0.4.0.db
```

Use a new destination and verify the backup before upgrading. A SQLite CLI/backup tool is
an alternative on Node versions without this optional backup API. Plain copying of an
active WAL database without its consistent journal state is not a reliable backup.
Campaign JSON files remain independent. Keep evidence epochs, artifact hashes and application
versions explicit when carrying working notes between sessions.
